# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Spring Boot 4 / Java 25 backend for Guillaume's website. It is mostly an API around Île-de-France Mobilités (IDFM) public transport data: it imports the IDFM GTFS into PostgreSQL (with PostGIS, used from SQL only: no geometry is mapped by JPA) and proxies IDFM PRIM real-time and Navitia APIs.

## Commands

```bash
./mvnw spring-boot:run                 # run locally (profile "dev" is active by default)
./mvnw clean package -DskipTests       # build jar (default Maven profile: -Pprod does not compile, the Swagger annotations come with springdoc)
```

Spring profiles: `dev` (default in `application.yml`, loads the gitignored `application-dev.yml` with the secrets; SQL and file logs) and `prod` (document in `application.yml`: no springdoc, logs on the standard output). `application-dev.yml` is left out of the jar (`maven-jar-plugin` exclude): production reads its secrets from `/etc/guillaumedamiens/application-prod.yml` (`--spring.config.additional-location`), CI from environment variables. Virtual threads and response compression are on for both.

## Production

Debian VPS, no Docker (human procedure in `README.md`). systemd service `guillaumedamiens` (`deploy/guillaumedamiens.service`, user `guillaumedamiens`, `-Xmx2g`, hardened: writes only to its private `/tmp`) running `/opt/guillaumedamiens/current.jar`, a link into `releases/`. nginx in front: `/api/` → `127.0.0.1:8080` with per-IP `limit_req`, access log without query strings (positions), JSON 503 while restarting; React site on `guillaumedamiens.com`, Flutter web app on `app.guillaumedamiens.com` (`/var/www/guillaumedamiens-app/current`); files in `deploy/nginx/`, applied by `deploy/nginx/apply.sh`. Deployment: tag `v*` → `.github/workflows/deploy.yml` uploads the jar as the `deploy` user (allowed to `systemctl restart guillaumedamiens` only) and runs `deploy/activate-release.sh` (switch, restart, wait for `GET /api/health`, roll back otherwise, keep 5 releases). `.github/workflows/build.yml` builds on each push and starts the jar against an empty PostGIS 18 (Liquibase + Hibernate validation): a new required extension must be created there too. `deploy/migrate-server.sh` did the one-time move from the former root service.

## Architecture

Package root: `com.gdamiens.website`.

- **Security** (`security/WebSecurityConfig`): stateless JWT via Spring's OAuth2 resource server (HS256, Nimbus encoder/decoder). Authorities come from the `auth` claim with no prefix: `ROLE_ADMIN` or `ROLE_USER` (stored in `user.role`, sign-up gives `ROLE_USER`; admin-only endpoints use `@PreAuthorize("hasRole('ADMIN')")`), or `ROLE_GUEST` for a device used without account (`Role.isGuest`). Open paths: `/api/signin`, `/api/signup`, `/api/auth/guest`, `/api/token/refresh`, `/api/logout`, `/api/health`, `/error` and Swagger/api-docs (dev only); `/api/v2/me/**` needs `ROLE_USER` or `ROLE_ADMIN`, the rest of the API any token. Guest tokens (`POST /api/auth/guest`, `UserService.createGuestToken`): JWT signed like the others, subject `guest:<uuid>`, 30 days, no refresh token, never stored; at most `application.budget.guest-tokens-per-ip-per-hour` per IP. Sign-in/up return a 1 h access JWT plus an opaque refresh token (`RefreshTokenService`: SHA-256 hash stored in `public.refresh_token`, rotated on each use, reuse revokes all the user's tokens). CORS origins come from `application.cors-allowed-origins` (`application.yml`, wider `localhost:[*]` list in the `dev` profile document). `RateLimitFilter` (Bucket4j, in-memory buckets in `RateLimiter`, added after the bearer filter) limits `/api/**` per minute: per IP on auth endpoints, per account or guest device when authenticated, per IP otherwise (`application.rate-limit.*`); 429 + `Retry-After`. `UsageBudgets` (on `RateLimiter`, longer buckets) caps the journey searches: per guest device and day, per account and day/hour (`application.budget.*`); 429 with problem detail `code` `journey_limit` (`guest_journey_limit` for a guest: signing in helps). Problem details may carry a stable `code` (`CustomException.getCode()`) the apps act on. Client IPs come from `X-Forwarded-For` via `server.forward-headers-strategy: native`
- **Controllers** (`controller/`): all under `/api`. `UserController` (sign-in/up, token refresh, logout), `HealthController` (`GET /api/health`: 200 when the database answers), `IDFMMainController` (GTFS import, admin) and the mobility API in `controller/v2/`.
- **Services** (`service/`): IDFM services extend `AbstractIDFMService` (provides API keys, `prepareHttpRequest()` headers and `consume(...)` for the quotas): `IDFMRealtimeService` (PRIM stop-monitoring and estimated-timetable, SIRI Lite), `IDFMNavitiaService` (journeys, places, traffic reports, walking paths; raw `JsonNode`), `IDFMMainService` (GTFS file link from Opendatasoft). External calls use `RestTemplate` on one shared Apache HttpClient 5 pool (`configuration/HttpClientConfig`: 3 s connect, 10 s read timeout or 60 s for bulk downloads, 50 connections per host, no automatic retry); URLs are centralised in `utils/Constants`.
- **Database schema**: owned by Liquibase (`resources/db/changelog/db.changelog-master.yaml`, formatted SQL changesets in `changes/`). Hibernate runs with `ddl-auto: validate` on the `public` entities (`user`, `refresh_token`, `favorite`): a change there needs a new changeset and matching entity types (e.g. `smallint` ↔ `Short`). Everything else lives in the `gtfs` schema, read with native SQL only (no JPA entity).
- **GTFS import**: `service/GtfsImportService` downloads the IDFM GTFS zip and streams each file into PostgreSQL with `COPY` (pgJDBC `CopyManager`), no Java row parsing. Each import clones the Liquibase-defined `gtfs` tables into `gtfs_new` (`LIKE`, without keys/indexes), loads them, runs `resources/gtfs/post_load.sql` (builds `shapes` LineStrings and the derived `route_stops`), copies keys and indexes from `gtfs`, then swaps `gtfs_new` → `gtfs` in the same transaction (failure = rollback, old data kept). Tables and columns use GTFS names (`gtfs.stops.stop_id`…); unknown header columns make the import fail until a changeset adds them. Triggered by cron in `IDFMUpdateBatch` (08:30 daily, 13:30 weekdays) or `POST /api/gtfs` (async, 409 if running).
- **Lines**: API line ids are IDFM ids (`C01371`), GTFS route ids are `IDFM:C01371` (`IDFMRoute.toRouteId/toLineId`). `TransportMode.fromGtfs()` maps `route_type` + agency (RER/TER/Transilien) + `N…` short names (Noctilien).
- **Mobility API v2** (`controller/v2/MobilityController`, `/api/v2/...`, DTO records in `controller/object/v2`): endpoints for the apps (nearby, stop area, departures, line, search). A stop area is a GTFS parent station (`location_type = 1`, `IDFM:71264`, every quay has one); it is also the SIRI stop-monitoring `MonitoringRef` (`STIF:StopArea:SP:71264:`) and the Navitia `stop_area:IDFM:71264`. GTFS reads go through `NetworkRepository` (`NamedParameterJdbcTemplate`, native SQL). `DepartureService` merges PRIM real time with GTFS scheduled departures for lines without real time, cached 30 s per stop area (`utils/TtlCache`, no cache library). `NetworkService.getLineDetail` groups trips by stop pattern, re-orients them (GTFS `direction_id` is unreliable, e.g. RER A) and merges express/short-turn patterns into branches. `SearchService`: lines matched locally, places from Navitia. `JourneyService` (`/api/v2/journeys`): Navitia journeys read as raw `JsonNode` (snake_case, only the needed fields) and mapped to options/sections with GTFS lines and stop areas; modes filter = forbidden Navitia physical modes; `earlier`/`later` cursors from Navitia's prev/next links. Navitia has no path for some trips (e.g. Transilien L direct trains: straight segments between stops); such rides (about one point per served stop) get the GTFS shape of their line cut between the two stops (`NetworkRepository.findShapeBetween`, PostGIS `ST_LineSubstring`), looked up in parallel within a 300 ms budget and cached 6 h. `FavoriteController` (`/api/v2/me/favorites`, user from the JWT subject): `public.favorite` rows (HOME/WORK one each, PLACE, STOP by stop area id, LINE by line id; partial unique indexes), returned with current GTFS stop/line data. `TrafficService` (`/traffic`, `/lines/{id}/disruptions`, `/stops/{id}/disruptions`): one Navitia `traffic_reports` call (PRIM has no `line_reports`; ~2 s, 25 MB) gives every disruption with its linked lines and stop areas; the snapshot is refreshed in the background when older than 2 min (stale served meanwhile and kept on failure); elevator outages are the `Ascenseur` tag, web messages are HTML turned into plain text. `VehicleService` (`/lines/{id}/vehicles`, cached 60 s: estimated-timetable quota): PRIM estimated-timetable of the line, calls at quays `IDFM:<id>` (or `IDFM:monomodalStopPlace:<id>` for RER) mapped to stop areas. Real vehicle journeys (SNCF, Métro 14) are matched against the line's branches (branch serving the next stop then most following calls in order). Most RATP lines and buses only give the next passages per stop under made-up journeys mixing vehicles (detected when > 20 % of journeys don't follow a branch): vehicles are then followed stop by stop along each branch (a passage continues the earliest vehicle seen at one of the two previous stops that can get there by then, since stops sometimes miss a vehicle; otherwise it is a vehicle that has left the previous stop; direction from the journey's destination). Progress between the stop left and the next one from the expected times. Each vehicle comes with its next calls (times, delay, platform) and, for SNCF, its mission code (`VehicleJourneyName`). `RideService` (`/lines/{id}/rides?from=&to=&after=`, cached 30 s per minute of `after`): the stop's departures of the line that stop at `to`, then the GTFS trips from `from` to `to` beyond what the stop lists (real time only goes so far), from `after` (a connection) on, with their arrival there from the stop-monitoring of `to` (`DepartureService.getArrivals`, shared 30 s cache of the raw calls: same train number, else the vehicle towards the same destination expected about when it should arrive; no estimated-timetable, its quota is small), else the GTFS trip (same train number = `trips.trip_short_name`, whose `trip_headsign` is the SNCF mission code) shifted by its delay, else the line's usual ride time (`typical`); numbered trains missing from the schedule between `from` and `to` are left out. `Departure.mission` / `trainNumber` come from stop-monitoring `VehicleJourneyName` / `JourneyNote`. `TimetableService` (`/stops/{id}/timetable?lineId=&date=`, cached 6 h): GTFS departures of a line over a service day, grouped by direction of the line detail (GTFS `direction_id` as fallback), same train under several calendars counted once. `BikeService` (`/bikes/stations`, `/bikes/nearby`): Vélib GBFS open data (station information every 6 h, status every minute, last data kept on failure). `journeys?bikeShare=true` adds a `bike_share` option built in `JourneyService` (closest station with a bike / with a dock within 600 m; walks to and from them estimated from the distance; the ride is Navitia's walking path between the stations, cached 24 h per pair, at 15 km/h: PRIM has no bike routing nor Vélib stations). PRIM's Navitia quota is small: no isochrones / heat maps, and new Navitia calls must be cached. Errors as `ProblemDetail` (`MobilityExceptionHandler`)
- **External API DTOs**: `idfm/` holds the SIRI Lite types of stop-monitoring and estimated-timetable (`controller/object/CallUnit` flattens a stop visit); Navitia responses are read as `JsonNode`.

## PRIM quotas (per day, marketplace account) — design with them

Every external call must fit these; cache server-side and share one fetch between users. `service/ApiQuota` counts the calls made through `AbstractIDFMService.consume(...)` and refuses above 90 % of the daily quota (callers fall back: no vehicles, schedule only…). Guest devices only get `application.quota.guest-share` (15 %) of each quota, at most 1/16 of it per hour, so the accounts always keep 75 %: the caller is read from the `SecurityContext`, so worker threads must get it (`DelegatingSecurityContextExecutorService`, as in `DepartureService` and `JourneyService`); background tasks count as accounts. Refusals are `QuotaExceededException` (503, `code` `quota_exhausted` / `guest_quota_exhausted`): a refusal of the guests' share must not be cached in a shared cache (departures and vehicles rethrow it out of the `TtlCache` loader and fall back for that caller only).

## Gotchas
- Stop ids : StopArea vs StopPoint vs monomodalStopPlace
- GTFS is theoretical while SIRI is realtime

## Other

- `Bruno/` is a Bruno (OpenCollection YAML) collection covering every `/api` endpoint: `Auth`, `Admin`, `Mobility (v2)` (`Auth / Guest token` stores a guest JWT in `guestJwt`). Auth is collection-level (bearer `{{jwt}}` + a before-request script in `opencollection.yml` that signs in with the environment's `username`/`password` when the JWT is missing or expiring). Example ids are collection variables. Add a request for each new endpoint.
